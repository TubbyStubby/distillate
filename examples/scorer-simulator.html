Matchmaking · scorer simulator guide

Simulating the matchmaker

We want to answer one question, fast: does a new scorer make better matches than the one in production? This page covers what a simulator for that needs, what it can leave out, and the order to build it in.

Short version: the simulator is a for loop in one Go process.

A matchmaker is a loop

Every 5 seconds the scheduler wakes up and does the same thing. New tickets join the pool and old ones expire. The scorer looks at every pair and says yes or no, with a score. The best pairs get matched and leave. Everyone else waits for the next tick.

Below, each dot is a ticket. Left to right is skill. The higher a dot sits, the longer that player has waited. The faint bar around each dot is the skill range the scorer accepts for that player, and it gets wider the longer they wait. Press Step to run one tick.

Most of production is plumbing

Production has a lot of moving parts: a matchmaking framework, a ticket store, a coordinator that collects proposals, RPC between services, Kubernetes. They let many pods share one queue safely. No ticket is matched twice, nothing is lost when a pod restarts, and it scales. Those are real problems, but they are consistency and scale problems. None of them decide who gets matched with whom.

In one process, a slice of tickets and a for loop do the job the framework and the ticket store were doing. So the simulator should not need Docker, the framework, a database, or a network connection. If it does, it is simulating the infrastructure instead of the matchmaking.

Replay over time, not one snapshot

It's tempting to grab one logged pool, score it with both scorers, and compare. The trouble is that each tick's pool depends on the scorer, because whoever wasn't matched last tick is still there. A strict scorer leaves more players waiting, their ranges widen, and later ticks look different.

We don't control who joins the queue. We do control who is still in it.

How to build it

  1. Get the inputs from logs

    Export the create and delete logs for a time window: every ticket with its createdAt, args and tags, plus when it was cancelled. Also export the per-tick pool logs and the match logs for the same window. You'll need them in step 3. Work from files; a live stream consumer isn't needed.

  2. Write the loop

    Import the real scorer through its Scorer interface instead of copying it. Keep production's pair rules, such as skipping pairs where both tickets belong to the same player.

    func Replay(arrivals []Ticket, newScorer func() Scorer) Result {
    sortByCreatedAt(arrivals)
    var pool []Ticket
    var res Result
    for now := firstTick(arrivals); !done(now); now += 5 {
        pool = append(pool, arrivedBy(arrivals, now)...)  // createdAt <= now
        pool = dropExpired(pool, now)                      // expiry, max ticket age, cancels
        pool = append(pool, botsDue(pool, now)...)         // bot fallback timer ran out

        sc := newScorer()
        sc.Prepare(pool, now)
        proposals := scoreAllPairs(sc, pool, now)          // same pair rules as production
        sc.Done()

        matches := greedy(proposals)                       // best score first, no ticket twice
        pool = removeMatched(pool, matches)
        res.Record(now, matches, pool)
    }
    return res
}

  3. Check it against production

    Replay a day with the production scorer. For each tick, compare your pool and matches with the logged pool and matches for the same tick. They won't agree perfectly, because cancel timing and failed assignments add noise, but they should be close. A large gap means the loop is wrong, and every scorer comparison built on it would be wrong too. Don't skip this step.

  4. Compare scorers, one run each

    Give each scorer its own full replay over the same arrivals. Never put two scorers into one shared pool. Then compare three things: match quality (skill gap, score), time to match (median and p90), and who didn't match (expired, bot fallback).

  5. Make iterating cheap

    The point is to try lots of scorer ideas. Aim for a day of replay in under a minute and measure it early. Run it as a Go test or a small CLI that prints a comparison table. Have Score return a reason when it rejects a pair, so you can see why players weren't matched.

Where to spend your time

Focus on

  • The tick order: arrive, expire, add bots, score, pick, remove
  • The real scorer code, imported, not rewritten
  • A greedy pick that behaves like production's evaluator
  • Same input, same output: no time.Now(), ties broken by ticket id
  • Speed, measured from the first version
  • Clear metrics and rejection reasons

Leave out

  • The matchmaking framework, the ticket store and the coordinator
  • Docker, Kubernetes and gRPC services
  • Live event streams; read exported files instead
  • Wall-clock time and sleeps; time is just now
  • Frontend, WebSockets and server allocation; a match just leaves the pool

What it can't tell you

Arrivals are replayed as they happened, so they don't react to the new scorer. In real life, a player matched sooner may queue again sooner, and a player who waits too long may give up. Trust the simulator for comparing scorers over hours of traffic, and confirm big changes with a small production experiment.

Synthetic tickets, for questions the logs can't answer

Logs only cover days that already happened. To ask "what if" you need tickets that never existed: a launch weekend at three times normal traffic, a quiet night, a new match type, a sudden wave of top-ranked players, or one odd edge case you want to pin down.

Synthetic tickets go into the same replay loop as logged ones. To the loop they are just another []Ticket. They never go through the production matchmaker.

Arrivals have a shape

The quickest generator spaces tickets evenly, one every few seconds. Real queues don't look like that. Players arrive at random, in clumps, and traffic rises and falls through the day. Pick a shape below and compare the start, middle and end of the run.

Over the whole run the averages come out about the same for every shape, which is exactly the trap. With rush-hour traffic, players in the busy middle match quickly and players in the quiet stretches wait much longer. Evenly spaced arrivals never produce a quiet stretch or a crowd, so they hide both.

Get the shape from the logs: count arrivals per minute for a real day, scale that curve for your scenario, then draw random arrivals within each minute. Report results per period, not only as one average.

A ticket's fields belong together

Fields on a ticket are related. Higher-ranked players tend to have higher ratings, and rank, rating and win rate move together. If you generate each field from its own histogram, every field looks right on its own, but you get players who couldn't exist, like a low-rank account with a top-tier rating. The scorer's checks then see pairs it never sees in production.

The histograms on the two edges never change. Each field on its own looks right in both modes. Only the combinations change, and the scorer works on combinations.

The simple fix is to resample whole real players from the logs and change only what the scenario is about, such as arrival times or the share of top-ranked players.

How to build the generator

  1. Start from real players

    Sample whole tickets from a real day's create log, with all their args and tags kept together. Give each copy a fresh ticket id and player id, so the same-player rule still works.

  2. Shape the arrivals

    Take the per-minute arrival curve from the same logs. Scale it for the scenario, for example ×3 for a launch or ×0.2 for a quiet night, and draw random (Poisson) arrivals inside each minute.

  3. Move the time fields with the ticket

    Set createdAt from the new arrival time, and shift its other timestamps (expiry, fallback timers) by the same amount, so each copy keeps its real offsets.

    type Scenario struct {
    Name      string
    Seed      uint64
    RateScale float64               // 3.0 = launch weekend
    Mutate    func(*Ticket)    // optional, e.g. raise the share of top-ranked players
}

func Generate(real []Ticket, perMinute []float64, start int64, sc Scenario) []Ticket {
    r := rand.New(rand.NewPCG(sc.Seed, 0))
    var out []Ticket
    for m, rate := range perMinute {
        for n := poisson(r, rate*sc.RateScale); n > 0; n-- {
            t := clone(real[r.IntN(len(real))])      // a whole player: fields stay together
            t.ID, t.PlayerID = freshIDs(r)
            shiftTimes(t, start+int64(m*60)+r.Int64N(60)) // all timestamps move together
            if sc.Mutate != nil {
                sc.Mutate(t)
            }
            out = append(out, t)
        }
    }
    return out
}

  4. Seed it and save it

    Always use a seeded random generator. Write the generated tickets to a file along with the seed and the scenario name, so anyone can rerun a comparison exactly.

  5. Check a 1× scenario against a real day

    Generate traffic at normal scale and replay it with the production scorer. Match rate, wait times and expiries should look like the real day. If they don't, fix the generator before trusting any "what if" it produces.

Where to spend your time on synthetic traffic

Focus on

  • Whole real players, resampled
  • Arrival curves taken from real logs, then scaled
  • Named scenarios, like "launch ×3" or "quiet night ×0.2"
  • A seed and a saved file for every scenario
  • Results per period, not just one average
  • The 1× check against a real day

Leave out

  • Pushing synthetic tickets into a live matchmaker or queue; that's a load test, and in production it pollutes real queues and metrics
  • Evenly spaced arrivals
  • Each field drawn from its own made-up range
  • Unseeded randomness

Logs tell you what happened. Synthetic tickets let you ask what might.

Rejections that explain themselves

A scorer that only says "no" leaves you guessing. Have Score return a short reason when it rejects a pair, plus the numbers behind the decision: both skills, the gap, the allowed range, how long each player waited. Count the reasons across a replay and the cause of long waits usually jumps out.

Plugging in scorers without a rebuild

Pasting a new scorer into a UI and running it straight away is great for quick experiments. The catch is speed. A common first attempt embeds a JavaScript interpreter and calls the script once for every pair, converting both tickets into JavaScript objects each time. A replay does that for every pair, every tick, 17,280 ticks a day, and it gets slow.

ApproachScript calls per tickTicket conversions per tickScript calls per simulated day

Exact counts, not timings. The bar is on a log scale.

The fix is the same whichever runtime you pick: convert each ticket once per tick, make one call with the whole pool, and get back every pair's result. That turns millions of crossings into one per tick.

Go scorer + config knobs

Good

Fastest, type-checked and reviewed like any other code. Most tuning is changing numbers, which config handles without a rebuild.

Costs

New logic needs a rebuild, which takes seconds.

Embedded JavaScript

Good

No rebuild, easy to write, runs in the same process.

Costs

An interpreter, so the maths is slow too. Every call pays to convert Go values to JS.

WebAssembly

Good

No host rebuild, compiled code that runs much faster than an interpreter, any source language.

Costs

An extra toolchain, and data has to be copied into wasm memory, so batching matters even more.

Start by exposing the scorer's numbers as config: ranges, thresholds, weights. Write new logic in Go, where a rebuild and a replay take seconds. Add script scorers only when people who don't write Go need to try ideas, and batch the calls from day one.

A workbench on top

Once the pieces above exist, a small UI ties them together and turns the simulator into something the whole team uses. Views worth building, roughly in this order:

  1. Comparison table

    Scorers side by side on quality, wait and unmatched players, split by period.

  2. Synthetic generator form

    Pick a scenario, a scale and a seed, then save the generated tickets so the run can be repeated.

  3. Tick drilldown

    For any tick: the pool, the proposals, the matches and the rejections.

  4. Reasons and journeys

    The two views above, on real replays.

  5. Export

    JSON or CSV of any view, for digging further in a notebook.

Keep the workbench a reader of replay output, built on the same engine as the CLI, so a result in the UI is the same result in a test. If it's hosted anywhere shared, put it behind a login and keep it off the production matchmaking services.
